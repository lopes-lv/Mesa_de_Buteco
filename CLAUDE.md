# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Python + Pygame desktop card/tile game ("Solo vs Bots") with three playable modes — Texas Hold'em, Pif Paf, and Dominó — sharing one tournament/elimination structure and one visual style ("Pixel Art Retrô CRT" — dark arcade palette, square corners, thick borders, hard offset shadows, monospace type, a scanline overlay) drawn entirely with `pygame.draw` (no external card/tile images). The style was "Neobrutalismo Suave / Dashboard Analítico" (light, rounded) before; `core/ui_theme.py`'s color/shape constants changed but every other module's call sites (buttons, panels, badges, avatars) did not, so touching the palette again means re-auditing which backgrounds need light vs dark text. `desenhar_botao` with `cor_texto=None` now picks the higher-contrast text itself (`ui_theme.cor_texto_sobre`, WCAG luminance — reproduces the old hand-kept list exactly: dark text only on YELLOW/MINT), but the many call sites that pass an explicit `cor_texto=SOMBRA/INK` (badges especially) don't adapt if a color is edited. Docs are in Portuguese; match that when editing them. Chips: only Hold'em uses them — in solo the human's stack is a persistent wallet (`core/carteira.py` → git-ignored `config/carteira.json`, 12 h wait after hitting zero); Pif Paf has no chips (first to `VITORIAS_PARA_VENCER` hand wins, Joker is the only wild card, no vira); Dominó scores points.

## Commands

```bash
pip install pygame
python main.py
```

`pygame` is the only runtime dependency. There is an automated test suite in `tests/` (297 tests, headless, ~10 s; see `tests/README.md`, requirements in `tests/REQUISITOS.md`):

```bash
pip install -r requirements-dev.txt
pytest -m "not lento"   # rules + structure, ~3 s (what CI runs on every push)
pytest -m lento         # bot-vs-bot full games + the editor's overlap matrix
```

Run it after touching any engine, `core/layout.py`, `rede/protocolo.py` or table geometry. Tests follow the per-mode READMEs; a rule the code doesn't meet yet is an `xfail(reason="BUG: ...")` listed in `tests/README.md` — don't loosen the test to make it pass. Tests never touch the real `config/layout.json` or `config/carteira.json` (`conftest.py` swaps them for temp files). Gameplay feel (hover, drag, animation) is still verified by playing. CI is `.github/workflows/ci.yml`.

Build a Windows executable (must be run on Windows, no cross-compile):
```bash
pip install pygame pyinstaller
pyinstaller PixelPoker.spec
```
The `.spec` embeds `config/layout_padrao.json` and `config/presets_padrao/*.json` (`datas`); the game won't start without the first, so a hand-typed command needs `--add-data "config/layout_padrao.json;config"` (plus the presets one).

## Architecture

Code is organized into packages by module: `core/` (shared shell), `holdem/`,
`pifpaf/`, `domino/` (one per game engine), `menus/` (pre-game/lobby screens),
`rede/` (multiplayer networking). `main.py` stays at the project root as the
entry point.

**Screen state machine.** `main.py`'s `App` holds `self.tela_atual` (current screen object) and swaps it via `ir_para_*` methods. Every screen implements `atualizar(dt)`, `desenhar(tela)`, `tratar_evento(evento)`. The main loop (`App.executar`) just delegates to whichever screen is current — new screens plug in by following this same trio of methods and getting a `ir_para_*` navigation method on `App`.

**Three parallel game engines, one shared shell.** Each mode has its own self-contained logic/AI/screen trio that never imports from the other's:
- Hold'em (`holdem/`): `game_logic.py` (`Player`, `BettingRound`, `Table`) + `hand_evaluator.py` + `bot_ai.py` + `table_screen.py` (host/local) + `mesa_remota_screen.py` (remote client)
- Pif Paf (`pifpaf/`): `pifpaf_logic.py` (`PifPafPlayer`, `PifPafTable`) + `pifpaf_bot_ai.py` + `pifpaf_screen.py` (host/local) + `mesa_remota_pifpaf_screen.py` (remote client)
- Dominó (`domino/`): `domino_logic.py` (`Peca`, `DominoPlayer`, `DominoTable`) + `domino_bot_ai.py` + `domino_theme.py` (tile drawing) + `domino_screen.py` (host/local) + `mesa_remota_domino_screen.py` (remote client)

All three share `core/` (`deck.py` — cards, Hold'em/Pif Paf only; `ui_theme.py` — all drawing primitives, panels, buttons, badges, cards; `ui_widgets.py` — `CampoTexto`, a one-line text input; `settings.py` — in-memory session settings, not persisted to disk; `chat_widget.py`), plus the `rede/` package and `menus/` (`screens.py`, `multiplayer_screens.py`) for multiplayer. `menus/multiplayer_screens.py:MAX_JOGADORES_POR_JOGO` is the single source of truth for the max seats a room of a given game allows (8 for Hold'em/Pif Paf, 4 for Dominó) — both `AnfitriaoSala.max_jogadores` and the bot-filling logic in `main.py` read it. Dominó also enforces a *minimum* of 3 (`LobbyScreen._pode_iniciar`, `ConfigScreen.min_bots` in `menus/screens.py`) since the tile-dealing math (see below) only works out evenly for 3 or 4 players.

**The palette, font scale and border/shadow are editable too.** `config/layout_padrao.json` also holds `cores.*` (the 16 `ui_theme` colors), `geral.escala_fonte`/`borda`/`sombra`, `geral.fichas_iniciais`, `geral.delay_bot_{lenta,normal,rapida}_ms` (read by `Settings`) and `pifpaf.delay_bot_ms`/`domino.delay_bot_ms` (the bot delays of those two screens). Every `ui_theme` color is a **mutable `pygame.Color`**, because every module does `from core.ui_theme import YELLOW` and so holds a reference to the same object: `ui_theme.aplicar_tema(obter)` updates the colors *in place* (and the font scale, applied inside `obter_fonte`, and the border/shadow defaults of `desenhar_painel`/`desenhar_botao`). It runs once at import with the user's layout. Consequences: never rebind a palette name (`ui_theme.YELLOW = ...` breaks the sharing); to add alpha write `(*COR[:3], alfa)` — a Color already has 4 channels, so `(*COR, alfa)` makes a 5-tuple; Colors aren't hashable (no dict keys/sets). The editor keeps its own interface on the default theme (`aplicar_tema(layout.padrao)`) and switches to the edited one only while drawing previews (`EditorVisual._tema_editado`), so a broken palette can't make the editor unreadable.

**Table-screen layout values live in `core/layout.py`, not in the screens.** Card/tile sizes, spacings and button sizes for all six table screens (host + remote client per mode) are read via `layout.obter("holdem.carta_jogador")` etc. from `config/layout_padrao.json` (each item: `valor` + `min`/`max`/`passo`/`rotulo`), overridden by an optional, git-ignored `config/layout.json` holding only changed items — a missing/corrupt file or a wrongly-shaped value silently falls back to the default, out-of-range values are clamped. Host and remote screens of a mode must read the *same* keys (they used to keep duplicated constants that could drift). Values are read at use time (not copied into module constants) and button `Rect`s are re-sized every frame, so a reload applies on the next frame: `main.App` reloads on **F5** and also polls `config/layout.json` once a second (mtime+size) and reloads by itself when it changes — i.e. when the editor saves with the game open (`App.recarregar_layout`: `layout.recarregar()` + `ui_theme.aplicar_tema()`; `Settings.fichas_iniciais` follows only if the player hadn't changed it this session; a short badge confirms it). `layout.py` also has presets: `listar_presets()`/`carregar_preset()`/`salvar_preset()`, same JSON shape as `layout.json`, shipped ones in `config/presets_padrao/` (compacto, grande — tuned with the editor's detector: compacto has zero alerts everywhere, grande only at 1600x900+), user ones in git-ignored `config/presets/` next to `layout.json`; `aplicar_ajustes(dict)` resets to defaults then applies a dict. The Ajustes screen has an "Editor de layout" button that launches `tools/editor_visual.py` as a subprocess (`menus/screens.py:editor_disponivel()` — source runs only; hidden when frozen). When a layout depends on a button's size, position it from `.width`/`midright` rather than a hardcoded offset, so edited sizes don't overlap. The visual editor `tools/editor_visual.py` (`python tools/editor_visual.py`; plan in `../.Viana/plano-editor-visual-poker-game.md`) edits these values in memory through `layout.definir()`/`salvar()` and previews each key at real size via `tools/editor_previas.py`, whose `PREVIAS` dict maps every key to a preview that re-implements that screen's geometry with the game's own draw functions. New tunable sizes should be added as keys in `layout_padrao.json` rather than as new constants — and every new key needs a `PREVIAS` entry too (the editor raises `KeyError` without one). If you change how a screen positions something that has a preview, update the matching preview so it stays faithful. The editor's "MESA COMPLETA" view (`tools/editor_mesa.py`) instead drives the *real* host screens: it builds a seeded bot match through `main.App.iniciar_partida*` on a fake app, lets "Você" play as a bot until a scene predicate holds (`CENAS`), then calls `tela.desenhar()` on an offscreen surface — temporarily patching `pygame.display.get_surface`/`pygame.mouse.get_pos` (some screens measure the window through it) and the draw functions each screen module imported by name (`desenhar_carta`, `desenhar_botao`, `desenhar_peca`, `desenhar_painel`, `desenhar_kbd`, `desenhar_badge`...) to record every element's rect for the overlap/off-screen alerts (`calcular_alertas`: off-screen; card/tile/button overlaps; card/tile/button partially inside a panel; button text under its key badge; a `desenhar_badge` selo over a panel unless fully inside it or pinned on its border like SB/BB, and over any button/card/tile; panels drawn *after the first button* — i.e. modals such as the raise or result panel, since every screen draws table/players/history → "Sair" → hand/controls → modals — only produce an "info" alert for what they cover, while fixed panels like the history are checked normally; repeated messages are merged with all their rects). `tools/editor_mesa.py:CENAS` is what the detector sees, so a state that never appears in a scene isn't checked (the Hold'em pre-flop scene exists because the player's own bet badge only shows there). So: draw new table elements through those `ui_theme`/`domino_theme` functions imported into the screen module (or they won't be checked), and if you rename a screen's state fields used by the `CENAS` predicates (`table.rodada_atual`, `mesa.pode_comprar()`, `fase_mao`, `resultado_mao`, `_comecar_proxima_mao_ou_finalizar`...) update them there too. Every table screen sizes its buttons in `_dimensionar_botoes()`, called at the start of each `desenhar()` so layout changes apply live — keep new layout-driven buttons in it. `tools/` is dev-only: not imported by `main.py`, not packaged in the `.exe`.

**Hold'em engine is a pure state machine.** `Table` orchestrates one hand (blinds → preflop → flop → turn → river → showdown) and doesn't know or care whether an action came from mouse input, `bot_ai.decidir_acao_bot`, or a network packet from `rede/anfitriao.py` (per `MULTIPLAYER_PLANO.md`) — every action flows through `rodada_atual.aplicar_acao(jogador, acao, valor)`. `Player.tipo` (`bot`/`humano_local`/`humano_remoto`) records the origin for whoever draws/decides the next action; `Table`/`BettingRound` never read it. `PifPafPlayer.tipo`/`DominoPlayer.tipo` mirror the same three values. Keep this decoupling when touching any engine: don't let it reach into UI or input state.

**Dominó is a 3-4 player points race to 250, no boneyard.** With 4 players the full 28-tile double-six set deals evenly (7 each); with 3, `domino_logic.criar_pecas()` removes the 0/0 tile so 27 tiles deal evenly too (9 each) — there's never a leftover pile, so there's no "comprar" (draw) action at all. `jogador_da_vez` either has a legal move (play a tile, choosing which end when it fits both) or doesn't, in which case they must explicitly click "Passar" (`DominoTableScreen._passar`/the network `acao_domino: passar` action) — bots and disconnected remote players auto-pass the same way `DominoTableScreen.atualizar()` used to auto-draw. Scoring replaces the old chip-stack economy entirely: `DominoPlayer.pontuacao` accumulates via (1) closing the open ends to a multiple of 5 on any play (`DominoTable.pontos_pontas`-style logic, doubles count both pips), (2) the batida bonus when someone empties their hand (opponents' remaining pips summed and rounded down to the nearest multiple of 5, +30 if the closing tile was a double), (3) +10 to whoever played immediately before someone passes, and (4) +50 if every other player passes in a row and it comes back to you still able to play ("trancar parcial" — the hand continues). If literally nobody (including that player) can move, the hand ends in `bloqueio_total`: lowest hand-points wins the same rounded-down sum, and the next hand resets to the "whoever holds 6/6 must open with it" rule (also true for hand #1 of the match). Every hand's opening move must be a carroça (double), no exceptions — hand #1 and every post-`bloqueio_total` hand forces the exact 6/6 (`peca_obrigatoria`); other hands let the previous winner pick *which* double to open with, among whatever they're holding (`jogadas_possiveis_em`'s empty-board branch filters the hand down to carroças-only, falling back to the full hand only if the opener holds no double at all — `DominoTable.jogar()` independently re-checks this, same "don't trust the UI alone" pattern as the bucho gate below). `DominoTable.vencedor_do_jogo()` is checked only once a hand actually ends (never mid-hand) and ends the whole match at 250+. See `PecaNaMesa` in `domino_logic.py` (fields `interno`/`externo`, direction-neutral) for how a played tile's visual orientation is tracked separately from `Peca`'s normalized identity — needed both for pip-matching rendering and for the multiple-of-5 scoring math.

**The board is a cross, not a line.** `DominoTable.ramos`/`extremidades` are dicts keyed by `domino_logic.DIRECOES` (`esquerda`/`direita`/`cima`/`baixo`), each an independent branch growing outward from `primeira_peca` (the hand's opening tile, kept separately as the board's center). Normally only `esquerda`/`direita` exist (a plain line, exactly like a single 2-ended chain). If `primeira_peca` is a double, `self.eh_spinner` flips on — every double is guaranteed a spinner on a forced-6/6 opening (hand #1, and any hand after a `bloqueio_total`), and possible-but-optional on a free opening. `cima`/`baixo` only actually become playable once `DominoTable.bucho_liberado()` is true (both `ramos["esquerda"]` and `ramos["direita"]` have at least one tile — the traditional "play both sides of the spinner before the bucho" rule); `jogadas_possiveis()` masks `cima`/`baixo` out of the extremidades dict it hands to `jogadas_possiveis_em()` until then, and `jogar()` independently re-checks `bucho_liberado()` before touching `ramos["cima"]`/`["baixo"]` (never trust the UI alone — the remote client mirrors the same gate locally in `_bucho_liberado()` just for preview/highlighting, but the host is what actually enforces it). Only the opening tile ever spins; a double landing later in any branch just renders rotated (see below) without creating a new branch. `jogadas_possiveis_em()` (the pure function shared with the remote client) is the single source of truth for which `(peca, direcao)` pairs are legal, and — critically — does **not** dedupe across directions once spinning, even when two branches currently expose the same pip value, because each direction is a physically different place to put the tile. `DominoTable.pontos_pontas()` only counts `cima`/`baixo` toward the multiple-of-5 score once a branch actually has a tile in it (being a legal target isn't enough).

**Table geometry must fit every window from 1024x768 to 1920x1080** — the editor's detector (`tools/editor_mesa.py`) reports zero problems in every mode × player count × window size × scene with the defaults; keep it that way (run the MESA COMPLETA view, or loop `simular_cena`/`desenhar_mesa`/`calcular_alertas` over `RESOLUCOES`, after touching seat angles/offsets). In all three games a seat's x is clamped so its panel stays on screen (`MEIA_LARGURA_ASSENTO`; the mesa is centred so the window width is `mesa_rect.centerx * 2`). Dominó: `domino_screen.py`'s `CENTRO_MESA_Y` (felt at 44% of the height), `FOLGA_ASSENTO_CIMA`/`FOLGA_ASSENTO_BAIXO` (top-half seats sit closer to the felt so the 4-player top seat stays on screen and clear of the "MÃO #n"/"Vez de" badges), `MEIA_LARGURA_ASSENTO` and `posicionar_botao_passar()` ("Passar" beside the hand) are imported by the remote screen. Pif Paf: `pifpaf_screen.py`'s `mesa_rect_para()`, `posicoes_assentos()`, `topo_da_mao()` (the hand never starts above the "Você" panel's bottom — it touched it at 768px height) and `posicao_selo_historico()` (the last-action badge drops below a seat panel it would cover) are imported by the remote screen. Hold'em (geometry still duplicated in `mesa_remota_screen.py` — change both): bet badges sit *beside* the cards (`_desenhar_selo_aposta`: yours to the right, bots' toward the table centre — below the cards yours hid behind Fold/Call/Raise and bots' hit neighbours/the history); `VAO_PAINEL_CARTAS_BOT` = 10px between a bot panel and its cards; 7-seat angles end at 35° (45° sat under the history panel) and 8-seat angles are `[90, 130, 165, 194, 228, 312, 348, 20]` (the 4 left seats are evenly spaced vertically — at 768px height that is the limit for panel+cards not to overlap); the Fold/Call/Raise row and the raise panel shift left of the history panel in narrow windows (`_limite_direito_controles`).

**Rendering doubles "deitadas" and drag-and-drop.** `domino/domino_screen.py`/`domino/mesa_remota_domino_screen.py`'s `_layout_mesa()` walks each active branch outward from the center tile, sizing every piece via `_tamanho_peca(direcao, eh_carroca)`: a normal tile's long axis follows its branch's growth axis, a double's is always perpendicular to it (reusing `domino_theme.desenhar_peca`'s existing `vertical=` flag — no theme-file changes needed) — this is also why a double advances the layout cursor less than a normal tile. A single scale factor is picked to fit both the horizontal (esquerda+direita) and vertical (cima+baixo) extents inside the felt at once — deliberately with no minimum-scale floor propping it back up (a branch with enough tiles just renders smaller, never overflows the felt). Branches are built in a local coordinate space with the center tile at `(0, 0)` first, then the whole assembly (every tile rect *and* every drop zone) is translated once so their union's center lands on `mesa_rect.center` — branches are rarely symmetric in a real game (way more tiles played left than right, say), so centering the spinner tile itself instead would let the longer side poke out past the felt even though the total width fits. There's no more click-to-select-then-click-a-zone: `tratar_evento` starts a drag on `MOUSEBUTTONDOWN` over a legal hand tile (`peca_arrastando`), follows the cursor on `MOUSEMOTION`, and on `MOUSEBUTTONUP` either applies the play if the cursor is over one of that tile's `zonas_drop_ativas` (computed per-drag from the previous frame's `_zonas_mesa`, restricted to *that piece's* legal directions) or does nothing (the tile was never removed from `mao`, so it just reappears in the tray).

**Hand evaluation via tuples.** `hand_evaluator.py` scores a 5-card hand as a tuple `(categoria, desempates...)` where larger tuples win — this makes comparison, tie-breaking, and split-pot detection just Python tuple comparison (`>`, `<`, `==`). Preserve this shape if you extend it (e.g. new categories or kicker rules).

**Side pots.** `calcular_potes()` in `game_logic.py` computes main pot + side pots from each player's `total_apostado_mao`, supporting partial all-ins, then merges consecutive pots with identical eligible-player sets. Split-pot remainder chips go to whoever is closest to the dealer.

**Bot AI is per-mode and stateless-ish.** `bot_ai.py` (Hold'em) assigns each bot a fixed risk profile per match (tight/balanced/aggressive/tricky) and decides using hand strength, draws, pot odds, bet pressure, table position, and active opponent count. `pifpaf_bot_ai.py` (Pif Paf) and `domino_bot_ai.py` (Dominó) are each a single heuristic (no per-match profiles): Pif Paf only draws from discard when it actually reduces loose-card points, always knocks (`bate`) when possible, never discards the wild card; Dominó prefers a legal play that scores (multiple of 5 on the open ends, via `DominoTable.pontuacao_se_jogar`) over one that doesn't, then doubles, then the highest-point tile among what's left.

**Deprecated code kept for reference.** `core/ui_pixelart.py` (old pixel-art rendering) and `assets/assets.png` are unused by the current game (replaced by `core/ui_theme.py`'s vector style) but intentionally kept — see the "Visão e planos futuros" section of `README.md` (deck skins) for the rationale (possible future reintroduction as an alternate deck skin). Don't delete them without checking with the user; don't wire new features into them either.

**`design/` directory.** Contains standalone HTML mockups + technical guides for visual styles that were evaluated before implementation, plus a design-system reference. `design/07_pixel_retro_crt/` is the style actually implemented in Pygame (`core/ui_theme.py`, current); `design/01_neobrutalismo_suave/` was the previous implemented style, now superseded; `03_casino_minimalista/`, `05_cozy_flat/`, `02_dark_glassmorphism/`, `04_terminal_tatico/`, `06_art_deco_cassino/`, `08_synthwave_neon/`, `09_papel_vintage/`, `10_editorial_suico/`, and `11_zen_japones/` are validated-but-unbuilt alternatives (`design/index.html` is a small gallery over the last four, the ones with a full set of mockup screens). `design/baralhos/` has 8 standalone card-back/face skins (one per unbuilt style above, including a `pixel_crt` one) with their own `GUIA_BARALHOS.md` on wiring one into `ui_theme.desenhar_carta` — not yet integrated; the live "Padrão" card look in `ui_theme.py` was built independently, matching the current Pixel Art Retrô CRT style directly rather than importing that skin module. `design/avaliacao/AVALIACAO.md` is a pre-redesign visual review of the old Neobrutalismo screens, now mostly superseded (its accent-glyph and card-slot-outline findings were fixed as part of the Pixel Art reskin). None of `design/` is imported by the running app.
